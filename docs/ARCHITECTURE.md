# Архитектура OPDS Desk

Этот документ описывает текущую архитектуру локального desktop-приложения OPDS Desk. Он дополняет [Конфигурация OPDS Desk](CONFIGURATION.md): там приведены параметры и размещение данных, а здесь — роли компонентов и поток данных.

## Общая архитектура

Приложение — Windows desktop-приложение, собранное в одном Python-модуле `app.py`. В нём находятся Flask-приложение, провайдер OPDS 1.x, HTTP-клиенты, модели представления, HTML-шаблоны, обработчики очереди и код запуска desktop-окна. Внешние шаблоны, отдельный сервер приложений и отдельный сервис очереди не требуются.

Основной поток данных выглядит так:

1. Пользователь открывает desktop-окно и работает с Flask-интерфейсом.
2. Настроенный OPDS-источник загружается и разбирается как Atom feed.
3. Результаты поиска и навигации преобразуются в серверные представления страниц.
4. Для выбранных результатов поиска в SQLite создаются задания очереди со снимком метаданных книги.
5. Фоновый worker последовательно получает acquisition-файлы, проверяет их и помещает в локальную библиотеку.

```text
pywebview
    |
    v
Flask UI / routes
    |-- OPDS catalog / search
    |-- queue / scheduler / notifications
    v
acquisition downloader
    v
validators
    v
local library
```

Состояние имеет два уровня. Конфигурация, очередь и массовые задания сохраняются на диске. Короткоживущие registries и кэши находятся только в памяти процесса и после перезапуска создаются заново.

## Модель выполнения

Основной поток определяет папку данных приложения, загружает конфигурацию и прикладное состояние, создаёт Flask-приложение, загружает сохранённые массовые задания, открывает или восстанавливает SQLite-очередь, удаляет незавершённые временные файлы и запускает планировщик. При обнаруженном незавершённом run он запускает worker в режиме recovery. Затем основной поток создаёт окно pywebview.

Длительная работа не выполняется в request-обработчиках Flask:

- worker очереди работает в одном daemon-потоке `opds-queue-worker`;
- планировщик очереди работает в daemon-потоке `opds-queue-scheduler`;
- массовые задания запускаются в отдельных фоновых daemon-потоках;
- доступ к общим in-memory структурам защищён соответствующими lock-объектами.

В каждый момент времени worker очереди единственный: повторный запуск проверяет уже работающий поток и текущее сохранённое состояние очереди.

## Desktop-оболочка и Flask

При запуске pywebview получает Flask WSGI-приложение непосредственно как URL окна; отдельный вызов `app.run()` не используется. Окно имеет доступ к ограниченному Python API `DesktopApi`. Сейчас он нужен главным образом для выбора папки локальной библиотеки и завершения первоначальной настройки.

Flask обслуживает локальные HTML-экраны, формы и небольшие данные для обновления интерфейса. Встроенные шаблоны рендерятся через `render_template_string`; Flask session хранит контекст навигации. JavaScript использует API pywebview только на тех экранах, где требуется действие desktop-оболочки. Окно запускается с `private_mode=False`, поэтому браузерное состояние pywebview может сохраняться согласно его обычному поведению.

Маршруты логически делятся на настройку, главный экран и поиск, просмотр каталогов, очередь и её запуски, массовые задания, уведомления и служебные данные интерфейса. Ошибочные пользовательские GET-запросы получают HTML-экран с сохранением HTTP-статуса.

## OPDS 1.x

`OPDS1Provider` реализует клиентскую модель OPDS 1.x на Atom XML. Он проверяет, что корневой элемент является Atom feed, и преобразует его в `OPDSFeed` и `OPDSCatalogPage`.

Записи с acquisition-ссылками становятся публикациями `BookRecord`. Для них извлекаются заголовок, авторы, язык, категории, изображения, web-ссылка, related-каталоги и список acquisition-ссылок. Идентичность публикации содержит идентификатор источника и идентификатор элемента источника. Записи без acquisition-ссылок рассматриваются как навигационные `CatalogRef`. Для каждого каталога сохраняются идентификатор источника, URL, заголовок и классифицированный вид ссылки.

Навигационные ссылки распознаются по relation и MIME-типу. Параметры MIME нормализуются: имена не зависят от регистра, вокруг `=` допускаются пробелы, а одна пара двойных кавычек вокруг значения снимается. Это позволяет одинаково обработать обычную, пробельную и quoted-запись параметров `profile` и `kind`.

Текущая реализация ориентирована на OPDS 1.x Atom XML. Каталоги OPDS 2 на основе JSON не разбираются.

### URL и HTTP

URL OPDS нормализуются до выполнения запроса. Допускаются абсолютные `http` и `https` URL с именем хоста; фрагменты удаляются, а встроенные учётные данные в URL не принимаются. Относительные `href` разрешаются относительно страницы, из которой они получены, и затем проходят ту же нормализацию. Локальные и частные сетевые адреса допустимы, так как приложение предназначено также для пользовательских OPDS-серверов в локальной сети.

`OPDSHTTPClient` использует `requests.Session`, User-Agent `OPDS-Desktop-Client/1.0`, timeout 15 секунд и потоковое чтение ответа с максимальным размером метаданных 10 МиБ. Redirect разрешён; итоговый URL ответа повторно нормализуется и используется как фактический адрес страницы.

Для временных HTTP-статусов 500, 502, 503 и 504, а также для timeout и connection ошибок выполняется до четырёх попыток с паузами 0,5, 1 и 2 секунды. Остальные ошибки HTTP и ошибки разбора не получают такой повтор автоматически. Проверка TLS и обработка системных прокси остаются стандартным поведением `requests`.

## Поиск и OpenSearch

Поиск начинается с discovery в корневом OPDS feed. Провайдер предпочитает совместимый OpenSearch descriptor; если источник предоставляет непосредственный Atom search template, он также может быть использован. OpenSearch description разбирается как XML и выбирает поддерживаемый search URL.

Шаблон поддерживает `{searchTerms}`, `{startPage}` и `{startPage?}`. `pageOffset` имеет тип integer и по умолчанию равен 1; отрицательное integer-значение не отклоняется. Некорректные нецелые значения descriptor делают этот вариант поиска неподдерживаемым. `totalResults`, если он объявлен источником и корректно читается, передаётся в представление страницы.

Номер страницы интерфейса начинается с нуля. Для первой страницы URL строится из шаблона, для следующих приложение следует по фактической цепочке Atom `rel=next`, а не предполагает арифметику URL. Циклы в цепочке страниц и превышение лимита в 500 страниц считаются ошибкой загрузки.

Выбор книг существует только на страницах результатов OPDS-поиска. Браузер хранит выбранные непрозрачные идентификаторы в `sessionStorage` на время текущего сеанса. При добавлении в очередь сервер заново разрешает эти идентификаторы через свой registry и не доверяет клиентским URL или метаданным книги.

## Навигация по каталогам

Для зарегистрированного OPDS-каталога URL не передаётся пользователю как параметр маршрута. Сервер регистрирует `CatalogRef`, выдаёт непрозрачный token и по нему загружает нужную страницу. Переходы Back, Next, Show all и Return to first page используют этот token и текущую страницу.

Обычный просмотр каталогов read-only: из его страниц не создаются элементы очереди. `rel=next` обрабатывается как последовательная цепочка страниц с обнаружением циклов и ограничением до 500 страниц. Режим показа всего каталога собирает эту же последовательность, а не выполняет неограниченный обход.

Для некоторых author-related каталогов есть консервативное одношаговое предпочтение: если родительская страница сама не содержит доступных книг и не имеет следующей страницы, приложение может открыть дочерний каталог с подходящим заголовком. Решение принимается только по известным заголовкам и проверенному содержимому дочерней страницы; рекурсивного обхода дерева нет.

## Registries и кэширование

### Catalog registry

`catalog_ref_registry` — in-memory упорядоченный registry ссылок каталогов. Его token строится из идентификатора источника и нормализованного URL, поэтому одинаковые URL разных источников не смешиваются. Максимум — 4096 ссылок; при переполнении удаляется самая старая. Registry не сохраняется на диск.

### Search book registry

`opds_search_book_registry` содержит серверные снимки книг из результатов поиска. Token строится source-aware из идентификатора источника, нормализованного query и идентификатора публикации. В registry может находиться до 8192 книг, после чего удаляются наиболее ранние записи. Именно этот снимок используется при создании записи очереди.

### Catalog cache

Кэш каталогов имеет два уровня: полные результаты и отдельные страницы. Ключи включают source ID, вид каталога и его идентификатор; у страничного кэша добавляется номер страницы. TTL обоих уровней — 15 минут. Принудительное обновление страницы очищает сохранённые последующие страницы той же цепочки, чтобы они не ссылались на устаревший `next`.

### Search cache

Кэш поиска хранит отдельные страницы 30 минут. Его identity — SHA-256 от source ID, OpenSearch template, MIME-типа descriptor, `pageOffset` и нормализованного поискового запроса; ключ страницы состоит из этой identity и номера страницы. Для удалённых страниц загрузчик использует сохранённого предшественника либо заново проходит цепочку с первой страницы. Принудительное обновление также инвалидирует последующие страницы этой search chain.

## Очередь загрузок

Очередь хранится в SQLite. Запись очереди содержит снимок книги, source-aware идентичность публикации, желаемый формат, приоритет, состояние, счётчики попыток, сведения об ошибке и происхождение действия. Активная запись для одной публикации того же источника защищена частичным уникальным ограничением SQLite, поэтому параллельные UI-действия не создают несколько pending или downloading элементов.

Основные состояния элемента — `pending`, `downloading`, `done`, `skipped` и `error`. Перед фактической загрузкой worker заново накладывает на сохранённый снимок идентификатор источника и публикации из SQLite, проверяет локальное наличие и свободное место. Тем самым runtime-обработка не зависит от изменяемого browser state.

### Worker очереди

Worker выбирает один pending элемент за раз в порядке приоритета и идентификатора записи. Он создаёт или продолжает сохранённый run, обновляет прогресс и попытки, определяет формат, сериализует фактическую загрузку глобальным lock и записывает итоговое состояние. Успешные, пропущенные и ошибочные элементы остаются в истории очереди и её запусков.

Worker учитывает паузу очереди и disk guard. Если run завершён без pending элементов, он финализируется и создаётся уведомление о завершении. Если выполнение остановлено, сохранённый run остаётся доступным для просмотра и продолжения.

### Планировщик

Планировщик просыпается каждые 20 секунд. Автоматический запуск по умолчанию выключен; его время, UTC offset и минимальный свободный остаток хранятся в настройках очереди. Когда запуск включён, очередь не поставлена на паузу, есть pending элементы и локальное время соответствует сохранённому расписанию, он запускает worker. Защита от повторного срабатывания хранит дату последнего запуска, поэтому один и тот же ежедневный момент не создаёт несколько runs.

## Загрузка книг

Загрузка acquisition-файла отделена от загрузки OPDS metadata. Для EPUB и FB2 используется отдельный `requests.Session`, потоковое чтение, connect/read timeouts 10 и 30 секунд, лимит 100 МиБ и до трёх попыток. Повторяются только классифицированные временные сбои; между попытками паузы увеличиваются.

Данные сначала записываются во временный файл. После успешной проверки готовый файл переносится в конечное место атомарной заменой. При каждой попытке временные артефакты очищаются. Режим Auto предпочитает EPUB и затем FB2; доступны только acquisition-ссылки поддерживаемых типов.

### Проверка EPUB

EPUB должен быть непустым ZIP-файлом в пределах лимита. Проверка включает CRC архива, точное значение `mimetype`, наличие `META-INF/container.xml`, XML-разбор container и наличие указанного им package-документа. Непрошедший проверку файл не считается успешно загруженной книгой.

### Проверка FB2

FB2 проверяется по размеру и XML-корню `FictionBook`. Acquisition может содержать raw FB2 или ZIP с FB2: для архива выбирается первый обычный FB2-файл, контролируется его распакованный размер, затем извлечённый файл проходит ту же XML-проверку.

## Локальная библиотека и дубликаты

Конечный путь строится внутри настроенной папки библиотеки из очищенных компонентов автора и названия. Ограничения длины компонентов предотвращают недопустимые или чрезмерно длинные имена файлов. Проверка локального наличия учитывает EPUB и FB2 рядом с ожидаемым путём.

Дубликаты определяются по нормализованным метаданным заголовка, авторов, языка и переводчика. При выборе предпочтительного издания сравниваются качество метаданных, изображения, доступность форматов и другие признаки записи. Режим сохранения дополнительного издания избегает коллизий имён файлов с помощью source-aware различия имени, не передавая URL источника в файловое имя.

## Сохранение состояния

| Объект | Формат | Назначение |
| --- | --- | --- |
| `config.json` | JSON | конфигурация OPDS-источника, каталога библиотеки и первоначальной настройки |
| `queue.db` | SQLite с WAL | надёжное состояние загрузок, runs и уведомлений |
| `jobs.json` | JSON | состояние длительных операций интерфейса |
| Flask session | cookie | контекст и URL возврата для навигации |
| Browser storage | sessionStorage/localStorage | краткоживущий выбор результатов поиска и состояние уведомлений интерфейса |
| Registries и кэши | память процесса | ссылки, снимки результатов и недавно загруженные страницы |

Расположение, структура и резервное копирование постоянных данных описаны в [Конфигурация OPDS Desk](CONFIGURATION.md). In-memory registries и кэши намеренно не являются источником восстановления после перезапуска.

## Восстановление после перезапуска

При инициализации SQLite незавершённые downloading элементы возвращаются в pending-состояние. Незавершённый run либо финализируется, либо продолжается в режиме recovery; пользователю создаётся соответствующее уведомление. До этого очищаются остатки временных файлов загрузки. Сохранённая очередь, runs и массовые задания остаются доступны после перезапуска, а сетевые страницы и registries загружаются заново по мере обращения.

## Обработка ошибок

Ошибки настройки источника, некорректных параметров страницы, отсутствующих элементов registries и недоступных сущностей имеют HTTP-статусы 400 или 404 и отображаются как локальные HTML-страницы. Ошибки получения или разбора OPDS metadata отображаются пользователю как ошибки источника.

В очереди ошибка отдельной книги не останавливает обработку остальных элементов. Ошибка классифицируется для прогресса и решения о повторе, записывается в состояние элемента и видна в run history. Повторяемые сетевые сбои обрабатываются HTTP-клиентом metadata или downloader в соответствии с их раздельными политиками попыток.

## Границы безопасности

Приложение предназначено для локального desktop-использования. Внутренний Flask backend предназначен для локального использования внутри desktop-приложения и не должен напрямую публиковаться как общедоступный web-сервис. OPDS-источники могут использовать HTTP или HTTPS; для HTTPS применяется стандартная проверка TLS библиотеки `requests`. URL источников и acquisition-файлов проверяются на корректную схему, хост и отсутствие встроенных учётных данных. Redirect для сетевых запросов разрешён, поэтому итоговый URL также нормализуется. Подключение к локальным и частным адресам не блокируется сознательно: это необходимо для пользовательских OPDS-серверов в локальной сети.

Сетевые ответы metadata и файлы загрузок имеют ограничения размера; форматы EPUB и FB2 проходят структурную проверку до помещения в библиотеку. Загрузка записывает данные только во временные и конечные пути локальной библиотеки, а состояние приложения — в свою папку данных.

Конфигурация, SQLite-база очереди, JSON массовых заданий и browser storage не шифруются кодом приложения. Их следует рассматривать как локальные данные пользователя и защищать средствами учётной записи, файловой системы и резервного копирования.

## Ограничения текущей реализации

- Поддерживается OPDS 1.x Atom XML; OPDS 2 JSON не поддерживается.
- Одновременно используется один настроенный OPDS-источник.
- Просмотр каталогов read-only; добавление книг в очередь выполняется из результатов OPDS-поиска.
- Поддерживаемые форматы загрузки: EPUB и FB2; PDF, DJVU и MOBI не загружаются.
- Поиск зависит от OpenSearch descriptor или непосредственного Atom search template, предоставленного источником.
- Глубокий автоматический обход связанных каталогов отсутствует; предпочтение author-related дочернего каталога ограничено одним проверенным шагом.
- Кэши, registries и browser `sessionStorage` не переживают обычный перезапуск процесса как серверное состояние.
- Очередь обрабатывается одним последовательным worker; параллельные загрузки книг не выполняются.
- Основная реализация приложения, включая backend, встроенный UI и большинство подсистем, сосредоточена в `app.py`.
